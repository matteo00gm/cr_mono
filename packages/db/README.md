# `@catalogorosso/db`

Schema, migrations and the tenant-scoped access helper.

## Two folders, because they need different privileges

| Folder        | Runs as                                  | Holds                                      |
| ------------- | ---------------------------------------- | ------------------------------------------ |
| `bootstrap/`  | the master role (`rds_superuser` on RDS) | Extensions, database roles, schema grants  |
| `migrations/` | `app_migrate`                            | Tables, indexes, constraints, RLS policies |

The split is not organisational tidiness — it is the privilege boundary the RLS
design rests on:

- `CREATE EXTENSION` and `CREATE ROLE` require privileges `app_migrate` does not
  have. Granting them so that everything could live in one chain would give the
  role that runs on every deploy superuser-grade DDL.
- Tables must be **owned by `app_migrate`**, because the runtime role `app_rw`
  must not be their owner: `FORCE ROW LEVEL SECURITY` does not apply to a table's
  owner, so an app connecting as the owner has every policy silently disabled.
  Whoever runs a migration owns what it creates, which is why table DDL cannot
  simply be run as master either.

Bootstrap is idempotent and safe to re-apply. It is applied by hand today:

```sh
psql "$MASTER_DATABASE_URL" -f packages/db/bootstrap/0000_extensions.sql
```

Wiring bootstrap and migrations into a deployment still needs its own task —
P0 has no CD path that runs them against a stage, only CI and tests.

## Generating a migration

Migrations are generated from the Drizzle schema, never hand-written, so the
TypeScript definition and the SQL cannot drift:

```sh
pnpm db:generate          # writes packages/db/migrations/NNNN_name.sql
```

Anything the schema cannot express — RLS policies, data backfills — goes in a
`--custom` migration generated by the same command, so the journal stays the one
record of order.

Every migration gets a hand-written reverse in `migrations/down/` under the same
filename. Drizzle has no notion of a down migration; the up/down/up drill in
P0-40 does, and an irreversible migration found during an incident is a bad
time to learn that.

## Reaching the database

`withTenant()` is the only sanctioned entry point — see `src/with-tenant.ts`.
The connection factory is deliberately not exported from the package; `src/index.ts`
explains why.
